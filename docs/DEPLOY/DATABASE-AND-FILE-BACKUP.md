# 数据库、图片与配置备份

数据库和图片共同组成一份可恢复的作业档案。数据库保存图片文件名，单独恢复数据库可能造成答卷记录存在却打不开原图。当前项目数据库内的服务凭据也随快照保留，备份须加密并限制读取。

## 备份范围与频率

| 内容 | 方式 | 建议频率 |
| --- | --- | --- |
| SQLite | 将 DB 以 SQLite Online Backup API 备份到独立文件，并在该文件运行 `PRAGMA integrity_check`、`PRAGMA foreign_key_check` | 每日与每次发布前 |
| `uploads/` | 同批文件树快照或增量归档，保留原图及 PNG、相对路径与校验值 | 与数据库同一恢复点 |
| 配置 | 保存 Compose、反代配置、镜像摘要、文件属主和权限。实际 secrets 单独加密，与同一版本配置建立引用 | 配置变化时及发布前 |
| 审计与历史 | 教师修改记录包含在 DB 内。按产品保留政策决定应用删除备份目录是否另归档，避免递归包入历次备份 | 随快照或独立归档 |

每日整组备份优先使用短暂停写窗口。维护入口阻止新业务请求，待上传、批改、删除和后台任务结束，停止应用。使用只读 SQLite 连接做备份并同时复制图片和配置，确认文件清单后恢复服务。复制耗时超出维护窗口时，可先预同步图片，停写后做最终差异同步和 DB 备份。未来若使用文件系统快照，必须验证卷和数据库处于同一恢复点。SQLite 在线备份能取得一致的数据库视图，但单独在线备份无法保证图片目录同时一致。[SQLite Backup API](https://www.sqlite.org/backup.html)

每次包含环境、UTC 时间、版本、数据库与照片数量、体积、SHA-256 清单和配置版本。校验成功后加密送往异地存储，解密材料与备份分开保管。服务器备份凭据只授予所需写入和读取权限，删除权限与应用账户分开。建议保留最近 7 个日备份、4 个周备份、3 个月备份及当前和上个发布点，最终按学校约定和容量调整。定期检查备份过期删除、失败告警以及本机任务删除备份的增长。

## 恢复演练

1. 初次上线前和以后每月，从异地选择一个实际可用的完整备份。Staging 常规环境只放合成数据。后续如需验证生产备份，使用独立恢复区、必要授权和访问限制，关闭 OCR 外联。
2. 验证加密包可解密、清单校验一致。恢复到新目录，设置文件属主和权限。核对 SQLite 完整性及外键，检查 `pages` 和 `batch_photos` 引用的原图及展示图是否存在，比较对象数量和关键记录。
3. 用备份记录的镜像摘要和匹配的配置启动单实例。验证登录和跨教师隔离、照片预览、成绩、改判历史及 CSV/PDF 下载。未完成的 OCR 任务仅核对状态，不自动重放。
4. 记录恢复点、耗时、丢失范围及截图证据，演练环境到期清理。按演练结果确认目标。试点建议 RPO 24 小时（可接受的最大数据回退时间）、RTO 4 小时（允许的恢复时长）。部署前单独备份用于缩小版本回退窗口。

后续若经批准导入历史库，先做离线副本检查、分配合法归属并移除或轮换旧服务密钥，再用同一批 DB 和图片导入。生产备份及真实数据不进入 GitHub 或 CI 制品。
